# 1. Назначение документа

Настоящий документ определяет единые правила разработки проекта **AI Procurement Auditor**.

Его цель — обеспечить единый стиль кода, предсказуемую структуру проекта и одинаковые подходы к реализации функциональности независимо от количества разработчиков.

Все изменения в проекте должны соответствовать требованиям данного документа.

---

# 2. Цели разработки

Основные цели процесса разработки:

- единый стиль кода;
- высокая читаемость;
- простота сопровождения;
- минимальная связанность компонентов;
- высокая тестируемость;
- возможность безопасного расширения проекта;
- предсказуемое поведение системы.

Любое архитектурное решение должно оцениваться с точки зрения долгосрочной поддержки проекта.

---

# 3. Общие принципы

При разработке проекта используются следующие принципы.

## 3.1 Простота

Предпочтение всегда отдается простому решению.

Сложность добавляется только при наличии объективной необходимости.

---

## 3.2 Читаемость

Код читается значительно чаще, чем пишется.

Поэтому понятность важнее сокращения количества строк.

---

## 3.3 Разделение ответственности

Каждый модуль должен отвечать только за одну область системы.

---

## 3.4 Повторное использование

Повторяющийся код должен выноситься в общие сервисы или утилиты.

Дублирование бизнес-логики не допускается.
---

# 4. Структура проекта

Проект должен сохранять единую структуру каталогов.

```text
ai-procurement-auditor/

├── apps/
│   ├── users/
│   ├── companies/
│   ├── documents/
│   ├── pipeline/
│   ├── rules/
│   ├── reports/
│   └── audit/
│
├── config/
├── docs/
├── media/
├── static/
├── tests/
└── manage.py
```

Каждое Django-приложение отвечает только за собственную предметную область.

Создание новых приложений допускается только при появлении новой самостоятельной области ответственности.

---

# 5. Правила именования

Используются следующие соглашения.

## Python

- классы — `PascalCase`;
- функции — `snake_case`;
- переменные — `snake_case`;
- константы — `UPPER_CASE`.

---

## Django

Примеры:

```text
Document
DocumentService
DocumentRepository
DocumentSerializer
DocumentViewSet
DocumentAdmin
```

Названия должны отражать назначение объекта.

Сокращения без необходимости не используются.

---

# 6. Организация бизнес-логики

Backend строится по принципу разделения ответственности.

## View

Отвечает только за:

- получение HTTP-запроса;
- проверку входных данных;
- вызов сервиса;
- возврат HTTP-ответа.

---

## Service

Содержит основную бизнес-логику.

Именно сервисы принимают бизнес-решения.

---

## Repository

Отвечает за получение и сохранение данных.

При необходимости допускается использование Repository Pattern поверх Django ORM.

---

## Model

Содержит структуру данных и минимальную доменную логику.

Сложные вычисления внутри моделей не размещаются.
---

# 7. Работа с ошибками

Backend должен обрабатывать все ошибки единообразно.

Ошибки делятся на категории:

- Validation Error;
- Business Error;
- Integration Error;
- Permission Error;
- System Error.

Пользователь получает понятное сообщение без раскрытия внутренней реализации системы.

Подробная информация записывается в журнал аудита.

---

# 8. Стандарты качества кода

Для проекта принимаются следующие требования.

Каждый новый модуль должен:

- иметь понятное назначение;
- содержать минимально необходимую связанность;
- быть пригодным для модульного тестирования;
- соответствовать архитектуре проекта;
- иметь понятные имена классов и методов.

При написании кода следует соблюдать рекомендации PEP 8.

---

# 9. Документирование кода

Документируются:

- публичные классы;
- сервисы;
- сложные методы;
- нестандартные алгоритмы.

Комментарии должны объяснять **почему** принято решение, а не **что** делает код.

Избыточные комментарии не используются.

---

# 10. Тестирование

Для каждого нового функционального модуля рекомендуется создавать тесты.

Минимальный набор тестов включает:

- проверку успешного сценария;
- проверку ошибочных входных данных;
- проверку граничных условий;
- проверку обработки исключений.

Приоритет отдается тестированию бизнес-логики сервисов.

Модели и представления тестируются по мере необходимости.
---

# 11. Работа с Git

Для проекта используется следующая стратегия.

## Коммиты

Каждый коммит должен:

- содержать одно логическое изменение;
- иметь понятное сообщение;
- не объединять несколько независимых задач.

Примеры сообщений:

```text
feat: add document upload

fix: validate supplier matching

docs: update api design

refactor: simplify pipeline service
```

---

## Ветки

Для MVP допускается разработка в основной ветке.

При переходе к командной разработке рекомендуется использовать:

- main;
- develop;
- feature/*;
- hotfix/*.

---

# 12. Code Review

Перед объединением изменений рекомендуется проверить:

- соответствие архитектуре;
- отсутствие дублирования;
- читаемость кода;
- корректность обработки ошибок;
- соответствие требованиям безопасности;
- наличие необходимых тестов.

Code Review рассматривается как обязательный этап контроля качества.

---

# 13. Definition of Done

Любая задача считается завершенной, если:

- реализована требуемая функциональность;
- код соответствует архитектуре проекта;
- соблюдены соглашения по именованию;
- отсутствует дублирование бизнес-логики;
- обработаны ошибки;
- обновлена документация (при необходимости);
- успешно проходят тесты;
- изменения зафиксированы в Git.
