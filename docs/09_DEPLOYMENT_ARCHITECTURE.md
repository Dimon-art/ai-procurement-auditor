# 1. Назначение документа

Настоящий документ определяет архитектуру развертывания системы **AI Procurement Auditor**.

Цель документа — описать принципы размещения компонентов системы, организацию окружений разработки и эксплуатации, а также требования к надежности, масштабируемости и сопровождению.

Архитектура развертывания должна обеспечивать возможность постепенного перехода от MVP к коммерческой B2B-платформе без изменения основных архитектурных решений.

---

# 2. Цели архитектуры развертывания

Deployment Architecture должна обеспечивать:

- простое локальное развертывание;
- воспроизводимость окружений;
- безопасное хранение данных;
- масштабируемость;
- надежность;
- возможность резервного копирования;
- мониторинг;
- централизованное журналирование.

---

# 3. Окружения системы

Для проекта определяются три основных окружения.

## Development

Используется разработчиками.

Особенности:

- локальный запуск;
- SQLite или PostgreSQL;
- локальное файловое хранилище;
- тестовые API OCR и LLM;
- включенный режим DEBUG.

---

## Staging

Используется для тестирования перед выпуском новой версии.

Особенности:

- конфигурация максимально приближена к Production;
- PostgreSQL;
- отдельное файловое хранилище;
- реальные интеграции OCR и LLM;
- отключенный DEBUG.

---

## Production

Используется конечными пользователями.

Особенности:

- высокая доступность;
- резервное копирование;
- мониторинг;
- журналирование;
- защищенные соединения;
- безопасное хранение секретов.

---

# 4. Общая схема развертывания

```text
Users
   │
   ▼
HTTPS
   │
   ▼
Reverse Proxy
   │
   ▼
Django Backend
   │
 ┌─┴───────────────┐
 ▼                 ▼
PostgreSQL     File Storage
                  │
          ┌───────┴────────┐
          ▼                ▼
       OCR API         LLM API
```

Backend является центральным компонентом системы и координирует взаимодействие всех остальных компонентов.
---

# 5. Компоненты инфраструктуры

Для MVP используются следующие компоненты.

## Django Backend

Является центральным компонентом системы.

Отвечает за:

- обработку HTTP-запросов;
- выполнение бизнес-логики;
- запуск AI Pipeline;
- работу с базой данных;
- взаимодействие с OCR и LLM.

---

## PostgreSQL

Основная база данных проекта.

Используется для хранения:

- пользователей;
- организаций;
- документов;
- результатов проверки;
- журналов аудита;
- настроек системы.

Все бизнес-данные должны храниться только в PostgreSQL.

---

## File Storage

Файловое хранилище содержит:

- оригиналы документов;
- подготовленные изображения;
- результаты OCR;
- сформированные отчеты.

Файлы не должны храниться внутри базы данных.

---

## OCR Provider

OCR выполняет распознавание текста документа.

Backend взаимодействует с OCR только через Adapter.

Это позволяет заменить поставщика OCR без изменения остальной системы.

---

## LLM Provider

LLM используется только для задач, определенных архитектурой:

- объяснение результатов;
- анализ нестандартных документов;
- AI-чат.

LLM не принимает бизнес-решения вместо Rule Engine.

---

# 6. Управление конфигурацией

Конфигурация приложения должна храниться отдельно от исходного кода.

Для хранения используются:

- `.env` — локальная разработка;
- переменные окружения — Production;
- секреты платформы развертывания.

В репозиторий запрещается добавлять:

- пароли;
- API-ключи;
- токены;
- секретные ключи;
- учетные данные базы данных.
---

# 7. Резервное копирование

Система должна поддерживать регулярное резервное копирование.

Резервному копированию подлежат:

- база данных PostgreSQL;
- файловое хранилище;
- журналы аудита;
- конфигурация системы.

Минимальные требования:

- ежедневное резервное копирование базы данных;
- регулярное резервное копирование файлов;
- проверка возможности восстановления;
- хранение нескольких последних резервных копий.

Резервные копии должны храниться отдельно от основного сервера.

---

# 8. Мониторинг

Система должна обеспечивать постоянный контроль состояния компонентов.

Контролируются:

- доступность Backend;
- доступность PostgreSQL;
- состояние файлового хранилища;
- доступность OCR Provider;
- доступность LLM Provider;
- использование памяти;
- использование процессора;
- свободное место на диске.

При обнаружении критических проблем должны формироваться уведомления администраторам.

---

# 9. Логирование

Backend должен централизованно журналировать:

- запуск Pipeline;
- ошибки обработки;
- обращения к OCR;
- обращения к LLM;
- ошибки API;
- действия пользователей;
- события безопасности.

Логи должны храниться отдельно от пользовательских данных.

---

# 10. Масштабирование

Архитектура должна поддерживать постепенное масштабирование.

В дальнейшем допускается:

- несколько экземпляров Backend;
- отдельный сервер PostgreSQL;
- выделенное файловое хранилище;
- очередь фоновых задач;
- несколько OCR Provider;
- несколько LLM Provider;
- балансировщик нагрузки.

Масштабирование не должно требовать изменения бизнес-логики приложения.
---

# 11. CI/CD

Для проекта предусматривается поэтапное внедрение непрерывной интеграции и доставки.

На этапе MVP достаточно автоматизировать:

- проверку качества кода;
- запуск тестов;
- проверку форматирования;
- сборку проекта;
- развертывание тестового окружения.

В дальнейшем рекомендуется использовать GitHub Actions как основную платформу CI/CD.

---

# 12. План развития инфраструктуры

Развитие инфраструктуры должно происходить постепенно.

### Этап 1 — MVP

- один экземпляр Backend;
- PostgreSQL;
- локальное файловое хранилище;
- один OCR Provider;
- один LLM Provider.

---

### Этап 2 — Pilot

Добавляются:

- резервное копирование;
- мониторинг;
- централизованное журналирование;
- отдельный сервер базы данных.

---

### Этап 3 — Commercial

Добавляются:

- несколько экземпляров Backend;
- балансировщик нагрузки;
- очередь фоновых задач;
- масштабируемое файловое хранилище;
- несколько OCR Provider;
- несколько LLM Provider.

---
