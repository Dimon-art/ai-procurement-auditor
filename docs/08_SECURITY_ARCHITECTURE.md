# 1. Назначение документа

Настоящий документ определяет архитектуру безопасности системы **AI Procurement Auditor**.

Цель документа — описать принципы защиты данных, пользователей, документов и внешних интеграций, а также определить требования к безопасной разработке и эксплуатации системы.

Безопасность рассматривается как часть архитектуры системы и должна учитываться на всех этапах жизненного цикла продукта.

---

# 2. Цели безопасности

Архитектура безопасности должна обеспечивать:

- конфиденциальность данных;
- целостность документов;
- доступность системы;
- аутентификацию пользователей;
- авторизацию операций;
- аудит действий;
- защиту внешних интеграций;
- безопасное хранение файлов;
- безопасное хранение учетных данных.

---

# 3. Основные принципы

При проектировании системы принимаются следующие принципы.

## 3.1 Least Privilege

Каждый пользователь и каждый сервис получают только минимально необходимые права.

---

## 3.2 Defense in Depth

Защита реализуется несколькими независимыми уровнями.

Нарушение одного уровня не должно приводить к компрометации всей системы.

---

## 3.3 Secure by Default

Все новые функции должны быть безопасны по умолчанию.

Дополнительная настройка безопасности не должна требоваться для стандартной эксплуатации.

---

## 3.4 Auditability

Все критические действия должны оставлять след в журнале аудита.

Это обеспечивает возможность расследования инцидентов и проверки действий пользователей.
---

# 4. Модель пользователей

В системе используются следующие роли.

## System Administrator

Отвечает за:

- настройку системы;
- управление пользователями;
- управление организациями;
- просмотр журналов аудита;
- администрирование.

---

## Company Administrator

Отвечает за:

- управление пользователями своей организации;
- настройку справочников;
- просмотр документов своей организации;
- управление параметрами проверки.

---

## Auditor

Отвечает за:

- просмотр документов;
- ручную проверку;
- подтверждение решений;
- работу с отчетами.

---

## User

Может:

- загружать документы;
- просматривать собственные документы;
- получать результаты проверки.

---

# 5. RBAC

Система использует модель **Role-Based Access Control (RBAC)**.

Все разрешения назначаются ролям.

Пользователь получает права только через свою роль.

Каждая операция Backend обязана проверять:

- подлинность пользователя;
- активность учетной записи;
- принадлежность организации;
- наличие необходимого разрешения.

При отсутствии разрешения возвращается ошибка **403 Forbidden**.

### 5.1 Роли MVP

Для MVP используются следующие роли:

- `operator` — загрузка документов и запуск обработки;
- `accountant` — просмотр и финансовая проверка документов;
- `manager` — контроль результатов проверки и просмотр отчетов;
- `company_admin` — управление пользователями своей организации и настройками организации.

Новые роли не добавляются без отдельной бизнес-потребности.

---

### 5.2 Tenant Isolation

Каждый пользователь принадлежит одной организации через `UserProfile.company`.

Защищенные операции Backend должны проверять не только роль пользователя, но и принадлежность объекта той же организации.

Пользователь не должен иметь возможность:

- просматривать документы другой организации;
- изменять документы другой организации;
- получать отчеты другой организации;
- управлять пользователями другой организации.

Проверка принадлежности организации выполняется на стороне Backend.

Frontend не считается механизмом защиты.

---

### 5.3 Запрет повышения собственных привилегий

Обычный пользователь не может изменять через собственный профиль:

- `role`;
- `status`;
- `company`.

Изменение роли, статуса учетной записи или принадлежности пользователя к организации является административной операцией и должно выполняться через отдельный защищенный Backend endpoint.

Обычный пользователь не может самостоятельно назначить себе роль `company_admin`.

Изменение ролей и прав доступа должно журналироваться в Audit Log.

---

# 6. Аутентификация

Для MVP используется JWT.

Backend поддерживает:

- Access Token;
- Refresh Token.

Пароли никогда не хранятся в открытом виде.

Для хранения используется современный алгоритм хеширования, поддерживаемый Django.

---

# 7. Авторизация

После успешной аутентификации Backend проверяет права доступа.

Проверяются:

- роль пользователя;
- принадлежность документа организации;
- допустимость операции;
- ограничения бизнес-логики.

Все проверки выполняются на стороне сервера.

Frontend не участвует в принятии решений о доступе.
---

# 8. Защита документов

Документы являются основным активом системы.

Для каждого документа должны обеспечиваться:

- безопасное хранение;
- контроль доступа;
- защита от удаления;
- контроль целостности;
- журналирование всех операций.

Документ может быть открыт только пользователем, имеющим соответствующие права.

---

# 9. Защита файлового хранилища

Файлы не должны быть доступны по прямым URL.

Доступ к файлам осуществляется только через Backend после проверки прав пользователя.

Для каждого файла сохраняются:

- уникальный идентификатор;
- дата загрузки;
- владелец;
- SHA-256 Hash;
- размер файла;
- MIME Type.

При каждой загрузке выполняется проверка целостности файла.

---

# 10. Защита внешних интеграций

Интеграции с OCR Provider и LLM Provider выполняются через защищенные соединения.

Требования:

- использование HTTPS;
- проверка сертификатов;
- хранение API-ключей вне исходного кода;
- ограничение прав API-ключей;
- журналирование ошибок интеграции.

API-ключи не должны сохраняться в репозитории.

---

# 11. Управление секретами

Все секреты приложения хранятся отдельно от исходного кода.

К секретам относятся:

- SECRET_KEY Django;
- JWT Secret;
- API-ключи OCR;
- API-ключи LLM;
- параметры подключения к базе данных.

Для локальной разработки используется файл `.env`.

Для production рекомендуется использовать специализированное хранилище секретов.

---

# 12. Журналирование событий безопасности

Отдельно журналируются:

- успешные входы;
- неудачные попытки входа;
- изменение ролей;
- изменение прав доступа;
- удаление документов;
- изменение настроек безопасности;
- ошибки авторизации;
- ошибки интеграций.

Журнал безопасности не должен изменяться пользователями.
---

# 13. Защита API

Все конечные точки API должны быть защищены.

Backend обязан обеспечивать:

- обязательную аутентификацию защищенных ресурсов;
- проверку JWT для каждого запроса;
- защиту от перебора учетных данных;
- ограничение количества запросов (Rate Limiting);
- проверку входных данных;
- защиту от SQL Injection;
- защиту от XSS;
- защиту от CSRF (для сессионной аутентификации);
- защиту от загрузки вредоносных файлов.

Все проверки выполняются до начала обработки бизнес-логики.

---

# 14. Безопасность журналов

Журналы аудита и безопасности являются критически важными данными.

Требования:

- запрещено удаление записей обычными пользователями;
- запрещено изменение существующих записей;
- журнал должен содержать точное время события;
- каждая запись должна быть связана с пользователем или системным процессом;
- журнал должен быть доступен только администраторам и аудиторам.

Журнал используется для расследования инцидентов и контроля соблюдения требований безопасности.

---

# 15. Безопасность развертывания

При развертывании системы должны соблюдаться следующие требования:

- использование HTTPS;
- отключение режима DEBUG;
- использование защищенных секретов;
- регулярное обновление зависимостей;
- резервное копирование базы данных;
- резервное копирование файлового хранилища;
- контроль доступа к серверу;
- мониторинг состояния системы.

Все изменения конфигурации должны документироваться.
