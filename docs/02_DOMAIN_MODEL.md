# 1. Назначение документа

Этот документ описывает предметную модель AI Procurement Auditor.

Цель документа — зафиксировать:

- ключевые бизнес-сущности;
- ответственность каждой сущности;
- связи между сущностями;
- жизненный цикл документа;
- бизнес-инварианты;
- границы MVP;
- соответствие будущим Django-приложениям.

Документ не является физической схемой базы данных. Он определяет бизнес-модель, на основе которой позже будут спроектированы Django-модели и миграции.

---

# 2. Центральная сущность

Центральная сущность системы — `Document`.

Все основные процессы начинаются с документа и заканчиваются решением по документу.

Документ:

- принадлежит компании;
- загружается пользователем;
- хранит исходный файл;
- проходит OCR;
- получает извлеченные поля;
- проверяется правилами;
- связывается с поставщиком и основанием;
- получает оценку риска;
- при необходимости попадает на ручную проверку;
- хранит историю изменений и решений.

Упрощенная схема:

```text
Company
  └── Document
        ├── DocumentField
        ├── CheckResult
        ├── RiskAssessment
        ├── ReviewTask
        ├── AuditLog
        ├── DocumentRelation
        └── Supplier
```

# 3. Границы предметной области

MVP охватывает путь закупочного документа от загрузки до решения пользователя.

В предметную область входят:

- компании-клиенты;
- пользователи;
- поставщики;
- документы;
- страницы документов;
- извлеченные поля;
- связи между документами;
- результаты проверок;
- итоговая оценка риска;
- задачи ручной проверки;
- пользовательские решения;
- журнал аудита;
- базовые правила проверки.

В MVP не входят:

- платежи;
- банковские транзакции;
- полноценный бухгалтерский учет;
- складские остатки;
- сложное согласование;
- полноценный ERP-контур;
- машинное обучение на поведении пользователей;
- автоматическое финансовое решение.

# 4. Агрегаты

## 4.1. Company Aggregate

Корневая сущность: `Company`.

Компания представляет отдельного B2B-клиента SaaS-платформы.

Внутри компании существуют:

- пользователи;
- поставщики;
- документы;
- правила;
- настройки;
- отчеты.

Все данные компании должны быть логически изолированы от данных других компаний.

### Инварианты

- каждая бизнес-сущность должна быть связана с одной компанией;
- пользователь одной компании не должен видеть данные другой компании;
- поиск дублей выполняется только внутри компании;
- настройки правил применяются только к документам соответствующей компании.

---

## 4.2. Document Aggregate

Корневая сущность: `Document`.

Документ является основной единицей обработки.

Внутри агрегата документа находятся:

- страницы;
- извлеченные поля;
- связи;
- результаты проверок;
- оценка риска;
- задача ручной проверки;
- решения;
- события аудита.

### Инварианты

- документ всегда принадлежит одной компании;
- документ всегда имеет уникальный идентификатор;
- оригинальный файл не должен изменяться после загрузки;
- повторная обработка не должна создавать дубли полей и проверок;
- ручное исправление поля не должно уничтожать исходное OCR-значение;
- завершенный документ должен иметь итоговый статус;
- итоговое решение пользователя должно быть записано в аудит.

---

## 4.3. Review Aggregate

Корневая сущность: `ReviewTask`.

Задача ручной проверки создается для документа, если:

- найден высокий риск;
- недостаточно данных;
- OCR confidence ниже порога;
- документ требует решения пользователя;
- системное правило явно требует ручной проверки.

### Инварианты

- для одного документа в MVP должна существовать не более одной активной задачи ручной проверки;
- закрытая задача должна содержать результат;
- результат должен быть связан с пользователем, который принял решение;
- решение должно иметь дату и комментарий либо код причины.

# 6. Жизненный цикл документа

Основные статусы:

```text
UPLOADED
STORED
PROCESSING
OCR_COMPLETED
EXTRACTED
NORMALIZED
CHECKED
REVIEW_REQUIRED
APPROVED
REJECTED
CORRECTION_REQUESTED
FAILED
ARCHIVED
```

Основной путь:

```text
UPLOADED
  ↓
STORED
  ↓
PROCESSING
  ↓
OCR_COMPLETED
  ↓
EXTRACTED
  ↓
NORMALIZED
  ↓
CHECKED
  ├── APPROVED
  └── REVIEW_REQUIRED
        ├── APPROVED
        ├── REJECTED
        └── CORRECTION_REQUESTED
```

### Правила переходов

- документ не может перейти в `CHECKED`, пока не завершена нормализация;
- документ не может быть `APPROVED`, если существует активная обязательная review task;
- ошибка OCR переводит документ в `FAILED` либо `REVIEW_REQUIRED`;
- ручное решение должно завершать активную review task;
- повторная обработка не должна отменять уже принятое решение без нового события аудита.

---

# 7. Основные бизнес-инварианты

1. Любой документ принадлежит ровно одной компании.
2. Исходный файл неизменяем.
3. Значения OCR и ручные исправления хранятся отдельно.
4. Итоговый Risk Score рассчитывается кодом, а не LLM.
5. Любой критический риск должен иметь evidence.
6. Решение по документу принимает человек.
7. Все решения и исправления журналируются.
8. Поиск дублей не выполняется между компаниями.
9. Низкая уверенность OCR означает неопределенность, а не доказанное нарушение.
10. Повторная обработка должна быть идемпотентной.

# 8. Доменные сервисы

Доменные сервисы не являются отдельными микросервисами. В MVP это модули внутри Django-монолита.

## DocumentProcessingService

Отвечает за последовательность обработки документа.

## FieldNormalizationService

Нормализует даты, суммы, валюты и реквизиты.

## DuplicateDetectionService

Ищет точные и вероятные дубли.

## MatchingService

Сопоставляет документ с договором, заказом или приемкой.

## RuleEvaluationService

Запускает правила и создает `CheckResult`.

## RiskCalculationService

Вычисляет итоговый Risk Score.

## ExplanationService

Формирует краткое объяснение на основе фактов и результатов правил.

## ReviewService

Создает и закрывает задачи ручной проверки.

## AuditService

Создает записи аудита для значимых действий.

# 12. Риски модели

## Слишком много сущностей

Мера: реализовывать только сущности, необходимые основному пользовательскому сценарию.

## Смешивание OCR и бизнес-данных

Мера: хранить raw и normalized values отдельно.

## Смешивание правила и объяснения

Мера: `CheckResult` хранит факты; LLM только объясняет их.

## Потеря истории исправлений

Мера: ручные изменения сохраняются отдельно и журналируются.

## Сложная ролевая модель

Мера: использовать четыре роли MVP без динамического конструктора разрешений.
