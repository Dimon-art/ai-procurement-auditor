---

# 1. Назначение документа

Настоящий документ определяет архитектуру REST API системы **AI Procurement Auditor**.

API является единственной точкой взаимодействия между Backend и внешними клиентами.

Все операции выполняются через HTTP API.

Backend не предоставляет прямой доступ к базе данных.

---

# 2. Цели API

REST API должно обеспечивать:

- аутентификацию пользователей;
- управление организациями;
- загрузку документов;
- просмотр документов;
- запуск обработки;
- получение результатов проверки;
- просмотр отчётов;
- получение журналов аудита.

API проектируется независимо от пользовательского интерфейса.

Это позволяет использовать:

- Web Frontend;
- Mobile Client;
- внешние корпоративные системы;
- интеграции через API.

---

# 3. Архитектурные принципы

REST API строится на следующих принципах.

## 3.1 Stateless

Каждый HTTP-запрос содержит всю информацию, необходимую для его обработки.

Сервер не хранит состояние клиента между запросами.

---

## 3.2 JSON

Все запросы и ответы используют формат JSON.

---

## 3.3 Versioning

Все URL содержат номер версии API.

Пример:

```text
/api/v1/
```

Это позволит развивать API без нарушения обратной совместимости.

---

## 3.4 Единый формат ответов

Все ответы API используют одинаковую структуру независимо от типа запроса.

Это упрощает разработку Frontend и интеграций.
---

# 4. Структура URL

Все конечные точки API располагаются внутри версии.

Базовый префикс:

```text
/api/v1/
```

Примеры:

```text
/api/v1/auth/
/api/v1/users/
/api/v1/companies/
/api/v1/documents/
/api/v1/pipeline/
/api/v1/reports/
/api/v1/audit/
```

Каждый ресурс использует существительные во множественном числе.

---

# 5. HTTP Methods

Используются стандартные методы HTTP.

| Method | Назначение |
|---------|------------|
| GET | Получение данных |
| POST | Создание объекта |
| PUT | Полное обновление |
| PATCH | Частичное обновление |
| DELETE | Удаление объекта |

Backend должен использовать методы в соответствии со стандартом REST.

---

# 6. Общий формат ответа

Каждый успешный ответ имеет одинаковую структуру.

```json
{
  "success": true,
  "data": {},
  "message": null,
  "errors": []
}
```

Ответ с ошибкой:

```json
{
  "success": false,
  "data": null,
  "message": "Validation Error",
  "errors": [
    {
      "field": "file",
      "code": "required"
    }
  ]
}
```

Единый формат значительно упрощает разработку клиентских приложений.

---

# 7. Коды HTTP

Backend использует стандартные HTTP-коды.

| Код | Значение |
|------|----------|
| 200 | OK |
| 201 | Created |
| 204 | No Content |
| 400 | Bad Request |
| 401 | Unauthorized |
| 403 | Forbidden |
| 404 | Not Found |
| 409 | Conflict |
| 422 | Validation Error |
| 500 | Internal Server Error |

Использование нестандартных кодов не допускается.
---

# 8. Аутентификация

Все защищенные методы API требуют аутентификации пользователя.

Для MVP используется JWT (JSON Web Token).

Каждый запрос к защищенным ресурсам должен содержать заголовок:

```http
Authorization: Bearer <access_token>
```

Backend проверяет:

- подлинность токена;
- срок действия;
- права пользователя;
- принадлежность пользователя к организации.

При отсутствии или недействительности токена возвращается код **401 Unauthorized**.

---

# 9. API пользователей

Раздел пользователей предоставляет операции:

- регистрация;
- вход;
- обновление токена;
- просмотр собственного профиля;
- изменение профиля.

Пример URL:

```text
POST   /api/v1/auth/login/
POST   /api/v1/auth/refresh/
GET    /api/v1/users/me/
PATCH  /api/v1/users/me/
```

---

# 10. API организаций

API организаций позволяет:

- получить список организаций;
- создать организацию;
- изменить организацию;
- просмотреть сведения;
- удалить организацию (при наличии соответствующих прав).

Пример URL:

```text
GET    /api/v1/companies/
POST   /api/v1/companies/
GET    /api/v1/companies/{id}/
PATCH  /api/v1/companies/{id}/
DELETE /api/v1/companies/{id}/
```

---

# 11. API документов

Документы являются центральным ресурсом системы.

Основные операции:

- загрузка документа;
- получение списка;
- просмотр карточки;
- просмотр статуса обработки;
- запуск повторной проверки;
- получение итогового отчета.

Пример URL:

```text
POST   /api/v1/documents/
GET    /api/v1/documents/
GET    /api/v1/documents/{id}/
GET    /api/v1/documents/{id}/status/
POST   /api/v1/documents/{id}/recheck/
GET    /api/v1/documents/{id}/report/
```
---

# 12. API Pipeline

Pipeline предоставляет операции управления обработкой документов.

Основные функции:

- запуск обработки;
- получение текущего этапа;
- просмотр истории выполнения;
- повторный запуск обработки.

Пример URL:

```text
POST /api/v1/pipeline/{document_id}/start/
GET  /api/v1/pipeline/{document_id}/status/
GET  /api/v1/pipeline/{document_id}/history/
POST /api/v1/pipeline/{document_id}/restart/
```

Backend не допускает одновременный запуск нескольких Pipeline для одного документа.

---

# 13. API отчетов

После завершения проверки пользователь может получить итоговый отчет.

Отчет содержит:

- общую информацию о документе;
- извлеченные реквизиты;
- результаты Rule Engine;
- итоговый Risk Score;
- рекомендации системы;
- историю изменений статуса.

Пример URL:

```text
GET /api/v1/reports/{document_id}/
```

---

# 14. API аудита

Журнал аудита предоставляет историю действий пользователей и системы.

Пример URL:

```text
GET /api/v1/audit/
GET /api/v1/audit/{id}/
```

Каждая запись содержит:

- дату и время;
- пользователя;
- действие;
- объект;
- результат;
- описание события.

---

# 15. Обработка ошибок API

Все ошибки возвращаются в едином формате.

Пример:

```json
{
  "success": false,
  "message": "Validation Error",
  "errors": [
    {
      "field": "supplier",
      "code": "required",
      "description": "Supplier is required."
    }
  ]
}
```

Внутренние ошибки системы не раскрываются пользователю.

Подробности сохраняются только в журнале аудита.

---

# 16. Ограничение запросов

Для защиты системы применяется ограничение количества запросов.

Для MVP используются:

- ограничение по пользователю;
- ограничение по IP-адресу;
- ограничение на загрузку документов.

При превышении лимита возвращается код **429 Too Many Requests**.
---

# 17. Документирование API

Все REST API должны документироваться автоматически.

Для проекта используется OpenAPI 3.0.

Документация должна содержать:

- список всех эндпоинтов;
- параметры запросов;
- схемы ответов;
- примеры использования;
- возможные ошибки;
- требования к авторизации.

В качестве инструмента рекомендуется использовать **drf-spectacular**.

---

# 18. Производительность API

При проектировании API необходимо соблюдать следующие требования:

- минимальное количество запросов к базе данных;
- использование пагинации для больших списков;
- поддержка фильтрации;
- поддержка сортировки;
- выборочная загрузка связанных объектов;
- отсутствие дублирующих запросов.

Каждый эндпоинт должен иметь предсказуемое время ответа.

---

# 19. Безопасность API

Backend обязан обеспечивать:

- обязательную аутентификацию защищенных ресурсов;
- проверку прав доступа;
- защиту от перебора паролей;
- защиту от массовой загрузки запросов;
- защиту персональных данных;
- журналирование критических операций.

Все проверки выполняются на стороне Backend.
