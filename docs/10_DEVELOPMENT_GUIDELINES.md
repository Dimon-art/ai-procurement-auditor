# 1. Назначение документа

Настоящий документ определяет единые правила разработки проекта **AI Procurement Auditor**.

Его цель — обеспечить единый стиль кода, предсказуемую структуру проекта и одинаковые подходы к реализации функциональности независимо от количества разработчиков.

Все изменения в проекте должны соответствовать требованиям данного документа.

---

# 2. Цели разработки

Основные цели процесса разработки:

- единый стиль кода;
- высокая читаемость;
- простота сопровождения;
- минимальная связанность компонентов;
- высокая тестируемость;
- возможность безопасного расширения проекта;
- предсказуемое поведение системы.

Любое архитектурное решение должно оцениваться с точки зрения долгосрочной поддержки проекта.

---

# 3. Общие принципы

При разработке проекта используются следующие принципы.

## 3.1 Простота

Предпочтение всегда отдается простому решению.

Сложность добавляется только при наличии объективной необходимости.

---

## 3.2 Читаемость

Код читается значительно чаще, чем пишется.

Поэтому понятность важнее сокращения количества строк.

---

## 3.3 Разделение ответственности

Каждый модуль должен отвечать только за одну область системы.

---

## 3.4 Повторное использование

Повторяющийся код должен выноситься в общие сервисы или утилиты.

Дублирование бизнес-логики не допускается.
---

# 4. Структура проекта

Проект должен сохранять единую структуру каталогов.

```text
ai-procurement-auditor/

├── apps/
│   ├── users/
│   ├── companies/
│   ├── documents/
│   ├── pipeline/
│   ├── rules/
│   ├── reports/
│   └── audit/
│
├── config/
├── docs/
├── media/
├── static/
├── tests/
└── manage.py
```

Каждое Django-приложение отвечает только за собственную предметную область.

Создание новых приложений допускается только при появлении новой самостоятельной области ответственности.

---

# 5. Правила именования

Используются следующие соглашения.

## Python

- классы — `PascalCase`;
- функции — `snake_case`;
- переменные — `snake_case`;
- константы — `UPPER_CASE`.

---

## Django

Примеры:

```text
Document
DocumentService
DocumentRepository
DocumentSerializer
DocumentViewSet
DocumentAdmin
```

Названия должны отражать назначение объекта.

Сокращения без необходимости не используются.

---

# 6. Организация бизнес-логики

Backend строится по принципу разделения ответственности.

## View

Отвечает только за:

- получение HTTP-запроса;
- проверку входных данных;
- вызов сервиса;
- возврат HTTP-ответа.

---

## Service

Содержит основную бизнес-логику.

Именно сервисы принимают бизнес-решения.

---

## Repository

Отвечает за получение и сохранение данных.

При необходимости допускается использование Repository Pattern поверх Django ORM.

---

## Model

Содержит структуру данных и минимальную доменную логику.

Сложные вычисления внутри моделей не размещаются.
