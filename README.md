# AI Procurement Auditor

## 1. Что это за проект

**AI Procurement Auditor** — учебный MVP веб-приложения для первичной проверки закупочных и бухгалтерских документов.

Система помогает бухгалтеру или оператору быстрее пройти первичный разбор документа: загрузить файл, распознать текст, извлечь основные реквизиты и позиции, автоматически выполнить набор проверок и увидеть оценку риска на карточке документа.

Проект предназначен для демонстрации подхода «загрузка → OCR → проверки → риск», а не для замены профессиональной бухгалтерской экспертизы.

## 2. Зачем создан проект

Ручная первичная проверка счетов, УПД и похожих документов занимает время и зависит от внимания человека. Ошибки в реквизитах, дубликаты файлов, проблемы с суммами или датой можно пропустить.

Назначение текущего MVP — автоматизировать именно **первичную** обработку:

- принять документ;
- распознать текст (OCR);
- извлечь ключевые реквизиты и позиции;
- прогнать фиксированный набор правил;
- рассчитать оценку риска и показать понятный результат пользователю.

Проект **не обещает** полноценный бухгалтерский аудит и юридически значимую экспертизу документа.

## 3. Польза проекта

- экономия времени на первичном разборе документа;
- автоматизация базовых проверок после загрузки;
- выявление потенциальных проблем (формат, OCR, обязательные поля, поставщик, дубликаты, сумма, дата, НДС);
- единое отображение реквизитов, позиций и результатов проверок;
- числовая оценка риска и понятный итог для пользователя;
- быстрый переход к проблемному документу из списка (в том числе по сводным счётчикам риска).

## 4. Что реализовано сейчас

По текущему коду проекта реализовано:

- вход пользователя в систему;
- регистрация пользователя (с привязкой к компании);
- изоляция документов по компании пользователя;
- загрузка документов (PDF / изображения поддерживаемых форматов);
- OCR (провайдер настраивается; по умолчанию Yandex OCR, для разработки доступен mock);
- извлечение основных реквизитов документа;
- извлечение позиций документа (строки таблицы) и сохранение в БД;
- Rule Engine с набором правил R001–R010;
- расчёт суммарной оценки риска по результатам проверок;
- список документов со счётчиками:
  - всего документов;
  - требуют внимания;
  - высокий риск;
- карточка документа с:
  - статусом обработки;
  - итогом проверки и оценкой риска;
  - основными реквизитами;
  - позициями;
  - результатами всех проверок;
  - техническими/OCR-данными (в отдельном блоке);
- утверждение документа из веб-интерфейса (для документов, прошедших обработку).

## 5. Какие проверки выполняются

Система выполняет следующие проверки:

1. Проверка формата файла  
2. Проверка целостности файла  
3. Проверка качества OCR  
4. Проверка обязательных полей  
5. Проверка поставщика  
6. Проверка дубликата файла  
7. Проверка дубликата документа  
8. Проверка суммы  
9. Проверка даты  
10. Проверка НДС  

По результатам каждой проверки формируется статус, серьёзность, балл и пояснение. Итоговая оценка риска — сумма баллов последних результатов по каждому правилу.

## 6. Как работает сценарий

```text
Загрузка документа
    → OCR
    → извлечение реквизитов и позиций
    → проверки (Rule Engine)
    → расчёт риска
    → результат пользователю (список + карточка документа)
```

## 7. Технологический стек

Фактически используемые технологии текущего проекта:

- **Python 3.12** (локально и в Docker-образе `python:3.12-slim`)
- **Django 5.2**
- **Django REST Framework** + SimpleJWT (API)
- **SQLite** (основная БД по умолчанию)
- **Gunicorn** (production-сервер в Docker)
- **WhiteNoise** (раздача статики)
- **python-dotenv** (загрузка `.env`)
- **Yandex OCR** (опционально; также есть mock-провайдер)
- **Docker** (production-сборка)

В `requirements.txt` также указан драйвер PostgreSQL (`psycopg`) — на случай внешнего использования Postgres; текущая конфигурация проекта по умолчанию использует SQLite.

## 10. Настройка окружения

1. Создайте виртуальное окружение.  
2. Активируйте его.  
3. Установите зависимости из `requirements.txt`.  
4. Создайте файл `.env` на основе `.env.example`.  
5. Заполните необходимые переменные окружения.

**Важно:** реальные секреты и ключи в README и в Git не публикуются. Файл `.env` должен оставаться локальным.

Минимум для запуска Django (см. `config/settings.py`):

- `SECRET_KEY` — обязателен;
- `DEBUG` — для локальной разработки обычно `True`;
- при необходимости OCR:
  - `OCR_PROVIDER` (`yandex` или `mock`);
  - для Yandex: `YANDEX_OCR_API_KEY`, `YANDEX_FOLDER_ID` (см. `.env.example`).

Для production дополнительно обычно задают `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` и флаги secure-cookie.

## 11. Локальный запуск

Команды для Windows PowerShell из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Создайте `.env` (минимум `SECRET_KEY`; для локальной проверки без внешнего OCR можно использовать `OCR_PROVIDER=mock`).

Затем:

```powershell
python manage.py migrate
python manage.py runserver
```

Откройте в браузере: `http://127.0.0.1:8000/`

## 16. Ограничения текущего MVP

Проект является **MVP**.

Реальные ограничения текущей версии:

- поддержка типов документов ограничена текущим извлечением (в коде нормализуются, в частности, признаки УПД / счёта / накладной; не все виды первички покрыты);
- качество OCR зависит от качества исходного файла;
- часть реквизитов типичной формы УПД пока не извлекается (например, адреса сторон, основание, подписи/печать, банковские реквизиты самого документа);
- позиции извлекаются эвристически из OCR-текста и могут отсутствовать, если структура текста не совпала с ожидаемой;
- набор правил фиксированный (формат, целостность, OCR, поля, поставщик, дубликаты, сумма, дата, НДС);
- проект **не заменяет** бухгалтерскую экспертизу и не является юридически значимым заключением.

## 17. Возможное дальнейшее развитие

В дальнейшем можно расширить распознавание и специализированную проверку следующих типов документов:

1. Счёт-фактура  
2. Товарная накладная (ТОРГ-12)  
3. Акт выполненных работ  
4. Акт оказанных услуг  
5. Акт приёма-передачи  
6. Акт передачи имущественных прав  
7. Счёт на оплату  
8. Платёжное поручение  
9. Кассовый чек  
10. Товарный чек  
11. Приходный кассовый ордер (ПКО)  
12. Расходный кассовый ордер (РКО)  
13. Квитанция к приходному кассовому ордеру  
14. Банковская выписка  
15. Авансовый отчёт  
16. Транспортная накладная  
17. Товарно-транспортная накладная (ТТН)  
18. Корректировочный счёт-фактура  
19. Исправительный счёт-фактура  
20. Универсальный корректировочный документ (УКД)  

**Эти 20 типов сейчас не заявлены как уже поддерживаемые** — это план развития.

Также перспективны:

- специализированные правила под каждый тип документа;
- расширение набора извлекаемых реквизитов;
- улучшение OCR и устойчивости извлечения позиций;
- дополнительные отчёты для бухгалтера.
