# 1. Назначение документа

Настоящий документ описывает архитектуру backend-приложения системы **AI Procurement Auditor**.

Backend является центральным компонентом системы и отвечает за выполнение бизнес-логики, управление жизненным циклом документов, взаимодействие с OCR, Rule Engine, файловым хранилищем и LLM.

Документ определяет структуру Django-проекта, принципы разделения ответственности между компонентами и правила реализации сервисного слоя.

---

# 2. Цели Backend

Backend должен обеспечивать:

- прием HTTP-запросов;
- управление пользователями;
- управление организациями;
- загрузку документов;
- выполнение Pipeline;
- запуск Rule Engine;
- взаимодействие с OCR Provider;
- взаимодействие с LLM Provider;
- хранение результатов обработки;
- формирование отчетов;
- аудит всех действий.

Все бизнес-решения принимаются исключительно Backend.

Frontend не должен содержать бизнес-логику.

---

# 3. Основные архитектурные принципы

Backend строится на следующих принципах.

## 3.1 Разделение ответственности

Каждый компонент отвечает только за одну область системы.

---

## 3.2 Сервисный слой

Бизнес-логика не размещается в Django Views.

Основная логика реализуется в отдельных сервисах.

---

## 3.3 Независимость компонентов

OCR, Rule Engine, LLM и файловое хранилище взаимодействуют через интерфейсы (Adapters).

Это позволяет заменять внешние сервисы без изменения бизнес-логики.

---

## 3.4 Минимальная связанность

Компоненты должны зависеть от абстракций, а не друг от друга.

Это упрощает тестирование и дальнейшее развитие проекта.
---

# 4. Общая структура Django-проекта

Backend реализуется как единый Django-проект.

Структура MVP должна быть простой, понятной и легко расширяемой.

```text
ai-procurement-auditor/

├── apps/
│   ├── users/
│   ├── companies/
│   ├── documents/
│   ├── pipeline/
│   ├── rules/
│   ├── reports/
│   └── audit/
│
├── config/
│
├── docs/
│
├── media/
│
├── static/
│
├── tests/
│
└── manage.py
```

Каждое приложение отвечает только за собственную предметную область.

---

# 5. Django Apps

Backend разделяется на несколько независимых приложений.

## users

Отвечает за:

- пользователей;
- авторизацию;
- роли;
- права доступа.

---

## companies

Отвечает за:

- организации;
- поставщиков;
- справочники;
- настройки компании.

---

## documents

Отвечает за:

- загрузку документов;
- хранение метаданных;
- статусы;
- версии документа.

---

## pipeline

Оркестрирует выполнение всех этапов обработки документа.

Именно Pipeline определяет последовательность вызова компонентов системы.

---

## rules

Содержит Rule Engine и бизнес-правила проверки документов.

---

## reports

Формирует итоговые отчеты для пользователя.

---

## audit

Хранит журнал действий пользователей и системных событий.

---

# 6. Сервисный слой

Основная бизнес-логика размещается в сервисах.

Views должны выполнять только следующие задачи:

- принять HTTP-запрос;
- вызвать нужный сервис;
- вернуть HTTP-ответ.

Вся обработка документа выполняется внутри сервисного слоя.

Это делает код проще для тестирования и сопровождения.
---

# 7. Жизненный цикл HTTP-запроса

Каждый запрос проходит одинаковую последовательность обработки.

```text
Client
    ↓
URL Router
    ↓
View
    ↓
Service Layer
    ↓
Repository / ORM
    ↓
Database
    ↓
Response
```

View никогда не содержит сложной бизнес-логики.

Основная работа выполняется сервисами.

---

# 8. Работа с базой данных

Backend использует Django ORM.

Прямые SQL-запросы допускаются только в случаях, когда ORM не обеспечивает необходимую производительность.

Все операции чтения и записи должны выполняться через модели или репозитории.

---

# 9. Интеграция с OCR

Backend не зависит от конкретного OCR Provider.

Используется Adapter, который скрывает особенности внешнего API.

Pipeline взаимодействует только с единым интерфейсом OCR Service.

Это позволяет заменить поставщика OCR без изменения бизнес-логики.

---

# 10. Интеграция с LLM

LLM подключается через отдельный сервис.

Backend передает модели только необходимые данные.

LLM никогда не получает полный доступ к базе данных.

Основные задачи LLM:

- объяснение результатов проверки;
- анализ нестандартных документов;
- помощь при сопоставлении поставщиков;
- ответы в AI-чате.

Все решения Rule Engine имеют более высокий приоритет, чем ответы LLM.
---

# 11. Взаимодействие компонентов

Компоненты Backend взаимодействуют только через сервисный слой.

Общая схема взаимодействия:

```text
HTTP Request
      │
      ▼
Django View
      │
      ▼
Application Service
      │
 ┌────┼──────────────┐
 ▼    ▼              ▼
ORM  Pipeline    External APIs
 │       │         ┌──────┴──────┐
 ▼       ▼         ▼             ▼
DB   Rule Engine  OCR API     LLM API
```

Такое разделение уменьшает связанность компонентов и упрощает сопровождение проекта.

---

# 12. Обработка ошибок

Каждый сервис обязан корректно обрабатывать ошибки.

Ошибки делятся на несколько категорий:

- Validation Error;
- Business Error;
- Integration Error;
- External API Error;
- System Error.

Пользователь получает понятное сообщение без раскрытия внутренней реализации системы.

Подробная информация сохраняется в журнале аудита.

---

# 13. Логирование

Каждый сервис обязан записывать события в журнал.

Минимальный набор информации:

- дата и время;
- пользователь;
- Document ID;
- Company ID;
- выполняемый сервис;
- результат выполнения;
- код ошибки (при наличии);
- продолжительность выполнения.

Журнал используется для аудита и диагностики системы.

---

# 14. Безопасность

Backend обязан соблюдать следующие требования:

- проверка прав доступа перед выполнением операций;
- защита от несанкционированного доступа;
- безопасное хранение файлов;
- защита персональных данных;
- журналирование критических действий пользователей;
- контроль доступа к административным функциям.

Все проверки безопасности выполняются на стороне Backend.
