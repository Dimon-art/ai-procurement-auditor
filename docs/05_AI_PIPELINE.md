---

# 1. Назначение документа

Настоящий документ описывает архитектуру конвейера обработки документов (AI Pipeline) в системе **AI Procurement Auditor**.

Главная цель конвейера — провести документ от момента загрузки до получения итогового решения с минимальным использованием дорогостоящих LLM.

Архитектура строится по принципу:

> **Сначала максимально дешевые и детерминированные проверки, затем подключение LLM только при необходимости.**

Это ключевое архитектурное решение проекта.

Для MVP не допускается использование большой языковой модели как основного механизма обработки документов.

LLM является вспомогательным компонентом и подключается только для задач, которые невозможно надежно решить обычными алгоритмами.

---

# 2. Основные цели AI Pipeline

Конвейер обработки должен решать следующие задачи:

- принять документ;
- проверить корректность файла;
- подготовить изображение для OCR;
- получить текст документа;
- извлечь необходимые поля;
- нормализовать данные;
- выполнить бизнес-проверки;
- вычислить уровень риска;
- определить необходимость ручной проверки;
- при необходимости вызвать LLM;
- сформировать итоговый отчет.

Каждый этап должен быть независимым и иметь возможность повторного запуска без повторной загрузки документа пользователем.

---

# 3. Главный принцип архитектуры

Для коммерческого SaaS-продукта стоимость обработки документа является одной из ключевых метрик.

Поэтому Pipeline проектируется по следующему правилу.

```
                           │

                └──────────┬──────────┘

                           │

                           ▼

                ┌─────────────────────┐

                │ Field Extraction    │

                └──────────┬──────────┘

                           │

                           ▼

                ┌─────────────────────┐

                │ Normalization       │

                └──────────┬──────────┘

                           │
```

Данный порядок обработки запрещается изменять без изменения архитектурной документации.

LLM никогда не вызывается раньше выполнения всех детерминированных проверок.

---

# 4. Общий жизненный цикл документа

Каждый документ проходит фиксированную последовательность состояний.

```

Uploaded

↓

Validated

↓

Stored

↓

OCR Processed

↓

Fields Extracted

↓

Normalized

↓

Rules Executed

↓

Risk Calculated

↓

Manual Review (при необходимости)

↓

Resolved

```

Ни один этап не может быть пропущен.

Если этап завершился ошибкой, документ получает статус **Failed** и дальнейшая обработка прекращается до устранения причины.

---

# 5. Этап 1. Загрузка документа

### Назначение

Получить документ от пользователя.

Поддерживаемые форматы MVP:

- PDF
- JPG
- JPEG
- PNG

На первом этапе запрещается поддерживать:

- DOCX
- XLSX
- ZIP
- архивы
- электронные подписи
- CAD-документы

Это сознательное ограничение MVP.

### Проверки

Во время загрузки выполняются проверки:

- файл существует;
- размер файла не превышает установленный лимит;
- MIME Type соответствует разрешенному типу;
- расширение файла совпадает с MIME Type;
- файл не поврежден;
- вычисляется SHA-256 hash.

Hash становится главным идентификатором физического файла.

Именно он позволит обнаруживать повторную загрузку одного и того же документа независимо от его имени.

# 6. Этап 2. Проверка документа (Validation)

После получения файла система выполняет предварительную проверку.

Цель этапа — не тратить ресурсы OCR и AI на документы, которые заведомо не могут быть обработаны.

На данном этапе проверяется:

- доступность файла;
- размер;
- формат;
- целостность;
- возможность открытия;
- отсутствие повреждений.

Если документ не проходит проверку, создается запись в журнале аудита, а пользователю возвращается понятная причина отказа.

Обработка Pipeline на этом завершается.

---

# 7. Этап 3. Сохранение документа

После успешной проверки документ сохраняется.

Система сохраняет:

- оригинальный файл;
- SHA-256 Hash;
- размер;
- MIME Type;
- дату загрузки;
- пользователя;
- компанию;
- путь к файлу.

После сохранения исходный документ больше никогда не изменяется.

Любые преобразования выполняются только над копиями.

Это необходимо для аудита и возможности повторной обработки.

---

# 8. Этап 4. Предобработка изображения

Перед запуском OCR выполняется улучшение качества изображения.

В MVP допускаются следующие операции:

- автоматический поворот страницы;
- удаление лишних полей;
- исправление наклона;
- увеличение контрастности;
- перевод цветного изображения в оттенки серого при необходимости;
- очистка цифрового шума.

Запрещается изменять содержимое документа.

Предобработка должна только улучшать читаемость.

Результатом этапа является изображение, максимально подходящее для OCR.

---

# 9. Этап 5. OCR

На данном этапе вызывается внешний OCR Provider.

Pipeline не зависит от конкретного поставщика OCR.

В системе используется адаптер (OCR Provider Adapter), что позволяет заменить одного поставщика другим без изменения бизнес-логики.

Результатом OCR являются:

- полный текст документа;
- разбивка по страницам;
- координаты найденных блоков;
- confidence каждого распознанного элемента.

Полученные данные сохраняются в базе данных и могут использоваться повторно без повторного вызова OCR.

Это существенно снижает стоимость повторной обработки документов.

---

# 10. Этап 6. Извлечение полей

После OCR начинается извлечение бизнес-данных.

Для MVP извлекаются только поля, необходимые для проверки документа.

Обязательные поля:

- тип документа;
- поставщик;
- номер документа;
- дата;
- валюта;
- итоговая сумма;
- НДС;
- ИНН поставщика (если найден);
- КПП (если найден).

Каждое поле получает:

- исходное значение;
- нормализованное значение;
- confidence;
- страницу;
- координаты на странице.

Pipeline никогда не изменяет исходное OCR-значение.

Все исправления сохраняются отдельно.

# 11. Этап 7. Нормализация данных

После извлечения полей начинается их приведение к единому формату.

Цель нормализации — сделать одинаковыми значения, которые в документах могут быть записаны по-разному.

Например:

```

№000123

123

000123

```

после нормализации становятся

```

123

```

То же относится к:

- датам;
- денежным суммам;
- валютам;
- ИНН;
- КПП;
- банковским реквизитам;
- названиям поставщиков.

Нормализация должна быть полностью детерминированной.

Использование LLM на этом этапе запрещено.

Результатом этапа являются значения, пригодные для сравнения между документами.

---

# 12. Этап 8. Rule Engine

После нормализации запускается Rule Engine.

Это основной механизм принятия решений в MVP.

Rule Engine представляет собой набор независимых правил.

Каждое правило:

- получает документ;
- выполняет одну проверку;
- возвращает результат;
- не знает о других правилах.

Такой подход позволяет легко добавлять новые проверки без изменения существующих.

---

## Первые правила MVP

### Duplicate File

Проверяет совпадение SHA-256 файла.

Если найдено совпадение —

```

Risk

```

---

### Exact Duplicate

Совпадают:

- поставщик;
- номер;
- дата;
- сумма.

Если совпадают все поля —

```

Risk

```

---

### Near Duplicate

Проверяются:

- похожий номер;
- одинаковая сумма;
- близкая дата;
- похожий поставщик.

Такой документ получает

```

Warning

```

и передается человеку.

---

### Missing Required Fields

Проверяется наличие обязательных полей.

Например:

- отсутствует номер;
- отсутствует сумма;
- отсутствует поставщик.

Если отсутствует обязательное поле —

```

Manual Review

```

---

### Supplier Validation

Проверяется существование поставщика в справочнике компании.

Если поставщик отсутствует —

```

Warning

```

---

### Amount Validation

Если загружено основание

(договор, заказ или УПД),

сравнивается итоговая сумма.

При расхождении выше допустимого значения —

```

Risk

```

---

### Document Completeness

Проверяется:

- читаемость документа;
- наличие всех страниц;
- успешность OCR.

Если документ невозможно надежно обработать —

```

Manual Review

```

---

Каждое правило работает независимо.

Ошибка одного правила не должна останавливать выполнение остальных.

# 13. Этап 9. Расчет Risk Score

После выполнения всех правил система рассчитывает итоговую оценку риска документа.

Каждое правило имеет собственный вес.

Например:

| Правило | Вес |

|----------|----:|

| Duplicate File | 100 |

| Exact Duplicate | 100 |

| Near Duplicate | 60 |

| Amount Mismatch | 80 |

| Supplier Mismatch | 70 |

| Missing Required Fields | 50 |

| OCR Confidence Low | 40 |

Итоговый балл рассчитывается Rule Engine.

LLM никогда не участвует в вычислении Risk Score.

Это принципиальное архитектурное решение.

Результатом этапа являются:

- итоговый балл;
- уровень риска;
- список сработавших правил;
- объяснение каждого правила.

---

## Уровни риска

Для MVP используются четыре уровня.

### OK

Документ успешно прошел все проверки.

Никаких действий пользователя не требуется.

---

### Warning

Обнаружены незначительные расхождения.

Документ рекомендуется проверить.

---

### Risk

Обнаружены критические нарушения.

Документ не рекомендуется проводить без проверки.

---

### Manual Review

Система не смогла принять надежное решение.

Документ передается человеку.

---

# 14. Использование LLM

Использование большой языковой модели должно быть минимальным.

Это одно из главных требований проекта.

Цель MVP —

обрабатывать **80–90% документов без вызова LLM**.

LLM используется только тогда, когда стоимость вызова оправдана.

---

## Когда разрешено использовать LLM

LLM допускается использовать в следующих случаях.

### 1. Объяснение результата

Пользователь спрашивает:

> Почему документ получил статус Risk?

LLM формирует понятное человеку объяснение на основе уже готовых результатов Rule Engine.

---

### 2. Сложное сопоставление поставщиков

Например:

```

ООО Ромашка

ООО "Ромашка"

Ромашка, ООО

ROMASHKA LLC

```

Если обычные алгоритмы не смогли принять решение,

допускается вызов LLM.

---

### 3. Анализ нестандартного документа

Например,

OCR извлек текст,

но структура документа сильно отличается от ожидаемой.

LLM может помочь определить расположение нужных реквизитов.

---

### 4. Пользовательский AI-чат

Пользователь может задать вопросы:

- почему найден риск;
- какие поля отличаются;
- какие документы похожи;
- что означает конкретное правило.

Во всех остальных случаях Rule Engine остается главным механизмом принятия решений.

---

# 15. Когда использование LLM запрещено

LLM запрещается использовать:

- для поиска дублей;
- для проверки сумм;
- для сравнения дат;
- для сравнения ИНН;
- для проверки обязательных полей;
- для расчета Risk Score;
- для определения статуса документа;
- для проверки форматов;
- для определения размера файла.

Все перечисленные задачи решаются обычными алгоритмами.

Это обеспечивает:

- предсказуемость;
- скорость;
- низкую стоимость;
- одинаковый результат при повторной обработке.# 16. Этап 10. Ручная проверка (Manual Review)
  Если система не может принять надежное решение автоматически, создается задача ручной проверки.
  Документ не блокируется без объяснения причины.
  Каждая задача должна содержать:
  - идентификатор документа;
  - причину передачи на проверку;
  - список сработавших правил;
  - итоговый Risk Score;
  - извлеченные поля;
  - ссылки на связанные документы (если есть);
  - рекомендации системы.
  Пользователь должен видеть не только статус, но и основания, по которым система приняла такое решение.
  ---
  # 17. Финальное решение
  После завершения автоматической или ручной проверки документ получает окончательный статус.
  Допустимые статусы MVP:
  ```
  OK
  ```
  Документ прошел все проверки.
  ---
  ```
  Warning
  ```
  Есть незначительные замечания.
  ---
  ```
  Risk
  ```
  Выявлены критические проблемы.
  ---
  ```
  Rejected
  ```
  Документ отклонен пользователем.
  ---
  ```
  Approved
  ```
  Документ подтвержден после ручной проверки.
  ---
  Все изменения статуса фиксируются в журнале аудита.
  ---
  # 18. Обработка ошибок Pipeline
  Pipeline должен быть устойчивым к сбоям.
  Ошибка одного этапа не должна приводить к потере документа.
  Каждый этап обязан возвращать:
  - успешное выполнение;
  - код ошибки;
  - описание ошибки;
  - время выполнения.
  Типовые ошибки MVP:
  ### File Error
  Поврежденный файл.
  ---
  ### OCR Error
  OCR не смог обработать документ.
  ---
  ### Extraction Error
  Не удалось извлечь обязательные поля.
  ---
  ### Rule Engine Error
  Ошибка выполнения одного из правил.
  Остальные правила продолжают работу.
  ---
  ### External API Error
  Недоступен OCR Provider или LLM Provider.
  Pipeline должен сохранить документ и позволить повторить обработку позже.
  ---
  # 19. Логирование
  Каждый этап Pipeline журналируется.
  Минимальный набор данных:
  - Document ID;
  - Stage;
  - Start Time;
  - End Time;
  - Duration;
  - Status;
  - Error Code;
  - Error Message.
  Это позволит анализировать производительность и искать узкие места.
  ---
  # 20. Производительность Pipeline
  При проектировании MVP необходимо соблюдать следующие принципы.
  ## OCR вызывается один раз
  Повторная обработка использует уже сохраненный результат OCR.
  ---
  ## LLM вызывается минимально
  Целевой показатель:
  **не более 10–20% документов требуют обращения к LLM.**
  ---
  ## Проверки должны быть быстрыми
  Большинство Rule Engine проверок должны выполняться за миллисекунды.
  ---
  ## Повторная обработка документа
  Если изменилось только правило проверки,
  OCR повторно не запускается.
  Если изменился только Prompt,
  OCR и Rule Engine повторно не выполняются.
  Каждый компонент должен использовать результаты предыдущих этапов.
  ---
  # 21. Последовательность компонентов
  ```text

  ↓

  ↓
  ```

  Изменение порядка допускается только после изменения архитектурной документации.
