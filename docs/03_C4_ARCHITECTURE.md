# 1. Назначение документа

Этот документ описывает архитектуру AI Procurement Auditor по модели C4.

Цель документа — зафиксировать:

- контекст системы;
- основные контейнеры;
- ключевые компоненты;
- взаимодействие между пользователями, Django, PostgreSQL, файловым хранилищем, OCR API и LLM API;
- границы MVP;
- архитектурные ограничения;
- решения, обязательные для реализации.

Документ не описывает физическую схему таблиц и детали API. Эти вопросы будут раскрыты в отдельных документах.

# 2. Архитектурный стиль MVP

Для первой версии используется модульный монолит на Django.

Система состоит из:

- одного Django-приложения;
- одного PostgreSQL;
- локального или S3-совместимого файлового хранилища;
- одного фонового обработчика;
- одного внешнего OCR API;
- одного внешнего LLM API.

В MVP не используются:

- микросервисы;
- Kubernetes;
- Kafka;
- RabbitMQ;
- отдельный frontend;
- vector database;
- собственная OCR-модель;
- собственная LLM.

Главный принцип:

> Простая реализация сегодня, возможность расширения завтра.

# 3. C4 Level 1 — System Context

## 3.1. Пользователи

### Operator

Загружает документы и отслеживает статусы.

### Accountant

Проверяет спорные документы и принимает решение.

### Manager

Просматривает отчеты и статистику рисков.

### Company Administrator

Управляет пользователями, поставщиками и базовыми правилами.

---

## 3.2. Внешние системы

### OCR Provider

Принимает файл или изображение и возвращает распознанный текст, поля и confidence.

### LLM Provider

Формирует краткое объяснение уже найденных рисков.

### Object Storage

Хранит оригиналы документов и изображения страниц.

### Email Provider

Не обязателен для первой версии. Может быть добавлен позже для уведомлений.

# 6. Основной поток обработки

```text
1. Пользователь загружает файл
2. Upload Component сохраняет файл
3. Создается Document со статусом UPLOADED
4. Worker берет документ в обработку
5. OCR Component получает текст и страницы
6. Extraction Component создает DocumentField
7. Normalization Component нормализует значения
8. Duplicate Detection ищет дубли
9. Rule Engine выполняет проверки
10. Risk Calculation формирует итоговый риск
11. При наличии риска вызывается Explanation Component
12. Если нужен человек, создается ReviewTask
13. Пользователь принимает решение
14. Audit Component фиксирует результат
```

---

# 7. Поток без LLM

Для большинства документов:

```text
Upload
  ↓
OCR
  ↓
Extraction
  ↓
Normalization
  ↓
Rules
  ↓
Risk Score
  ↓
Approved
```

LLM не вызывается.

---

# 8. Поток с LLM

LLM вызывается только если:

- есть один или несколько рисков;
- требуется краткое объяснение;
- стандартного шаблонного текста недостаточно.

```text
Rules
  ↓
Risk Score
  ↓
Structured Facts
  ↓
LLM Explanation
  ↓
ReviewTask
```

В LLM передаются только:

- тип документа;
- основные поля;
- найденные расхождения;
- evidence;
- рекомендуемое действие.

Исходный PDF целиком в LLM не передается в MVP.

# 10. Архитектурные решения

## ADR-001 — Модульный монолит

Причина:

- один Junior-разработчик;
- быстрый старт;
- простая отладка;
- минимальная инфраструктура.

## ADR-002 — Django Templates вместо React

Причина:

- один стек;
- меньше кода;
- быстрее MVP;
- проще сопровождение.

## ADR-003 — PostgreSQL как единственная БД

Причина:

- транзакции;
- связи;
- JSON;
- индексы;
- зрелый Django support.

## ADR-004 — Внешний OCR

Причина:

- отсутствие GPU;
- отсутствие ML-команды;
- быстрый запуск;
- меньшая сложность.

## ADR-005 — LLM только для объяснения

Причина:

- минимальная стоимость;
- снижение галлюцинаций;
- детерминированный Risk Score;
- простая валидация.

## ADR-006 — Management Command как worker

Причина:

- отсутствие Redis;
- отсутствие Celery;
- минимальная инфраструктура;
- возможность заменить позже.

---

# 11. Надежность

Обязательные требования:

- повторный запуск обработки безопасен;
- каждая стадия сохраняет результат;
- ошибка OCR не удаляет документ;
- ошибка LLM не блокирует базовые проверки;
- документ может быть переведен в `FAILED`;
- пользователь видит причину ошибки;
- исходный файл сохраняется всегда.

---

# 12. Безопасность

Минимальные требования MVP:

- авторизация;
- роли;
- company isolation;
- проверка доступа к каждому документу;
- защита upload;
- ограничение размера файла;
- допустимые MIME types;
- хранение секретов в `.env`;
- audit log;
- запрет передачи лишних данных в LLM.

---

# 13. Наблюдаемость

Для MVP достаточно:

- Django logs;
- журнал ошибок worker;
- время обработки документа;
- статус каждой стадии;
- количество OCR ошибок;
- количество LLM вызовов;
- токены и стоимость LLM;
- количество документов в review.

OpenTelemetry не обязателен в первой версии.

---

# 14. Масштабирование

Текущая архитектура должна позволять позже:

- заменить management command на Celery;
- добавить Redis;
- вынести OCR в отдельный сервис;
- вынести LLM gateway;
- добавить S3;
- добавить REST API;
- добавить React frontend;
- добавить ERP-интеграции.

Эти изменения не входят в MVP.

# 15. Риски архитектуры

## Долгая обработка

Мера: отдельный worker и статусы.

## Ошибка внешнего OCR

Мера: retry и `FAILED`.

## Ошибка LLM

Мера: базовые проверки работают без LLM.

## Рост монолита

Мера: четкие Django apps и service layer.

## Смешивание бизнес-логики и views

Мера: логика размещается в services, а не в views.

## Сильная зависимость от поставщика

Мера: OCR Adapter и LLM Adapter.
